# Parameter registry (human view)

The source of truth is **`config/parameter_registry.yaml`**
(`blueboat_parameter_registry/1`). This page explains it; the table at the
end is generated by `python3 -m blueboat_sss_sim.calibration registry
--markdown`. Regenerate the table whenever the YAML changes.

## What the registry is for

1. **Provenance you can check.** Each important constant carries:
   - its unit, class and status;
   - its bounds and whether a calibration may move it;
   - how it would be identified and what it is confounded with;
   - the experiment that would fix it, and which code owns it.

   `sss_calibration registry --check` (and smoke `[16]`) fails if any
   `default` differs from what the model actually uses: the dataclass
   default, the shipped profile, a module constant, the material table or
   `config/sea_states.yaml`. It also fails if the shipped profile leaves a
   registered parameter implicit.
2. **The gatekeeper for calibration artifacts.** An artifact may set only:
   - registered, `tunable: true` parameters;
   - in the registered unit;
   - inside `bounds`;
   - per session, only for the `session_classes`.
3. **Not a configuration file.** Nothing reads a value from it at run time.
   A value changes in the code or profile first, as a deliberate and
   documented model change (NC #6). The registry is updated in the same
   change, or the gate fails.

## Status vocabulary (stricter than `sonar_model.md` §6)

| Status | Meaning |
|---|---|
| `physical` | physical constant or closed-form law, held |
| `spec` | specification or drawing, not measured on this boat |
| `measured` | read directly off field data by a stated reduction |
| `joint` | estimated together with other constants; only the set is identified |
| `estimated` | fitted or inferred from limited data (one recording, one target, a scan) |
| `literature` | cited source, site spread stated |
| `derived` | follows from other constants or the model's own equations |
| `judged` | judgement value, nothing constrains it |
| `undetermined` | held at a gated value or shipped off |
| `structural` | model switch or numerics |
| `run_setting` | chosen per run, never calibrated |

Where `sonar_model.md` §6 used a softer word, `doc_label` keeps its
wording. Two examples:

- `tvg_compensation` is "Measured on two altitudes at once" there and
  `joint` here: it came out of one fit together with `lambert_exponent`
  and `calibration_db_offset`.
- `beam_tilt_deg` is "Corpus-constrained" there and `estimated` here: a
  scan on one recording.

A value is never marked `measured` just because it sits in a config file.

## Adding or changing a parameter

1. Change the code or profile, with the evidence (NC #6;
   `docs/sonar_model.md` §6 for the acoustic constants).
2. Add or update its registry entry. All of these are required: `name`,
   `unit`, `class`, `status`, `default`, `tunable`, `meaning`,
   `identified_by`, `metric`, `uncertainty`, `confounders`, `experiment`,
   `owner`. Then add `bounds` (or `choices`) and a `source` for anything
   outside the sonar profile.
3. Run `python3 -m blueboat_sss_sim.calibration registry --check` and the
   smoke suite.

Not yet registered, but worth adding when they become identifiable:

- a timing latency (sonar vs navigation);
- a per-session level nuisance;
- the gain indices 1–3, 5 and 6;
- per-material roughness for every object material;
- the BlueBoat hydrodynamic coefficients. These are owned by
  BlueBoat-Control's `blueboat_description`; register them by reference
  only.
